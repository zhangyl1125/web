## 已实现的规则

| 规则 | 实现与核查依据 |
| --- | --- |
| 每人每赛道最多4票，不要求投满 | `VoteIdeaUseCase.execute` 读取 `app.voting.max-votes-per-track`，默认4；新增第五票拒绝，撤票不受上限拦截 |
| 各赛道、各评选独立计票 | 先按用户与评选查询选票，再按规范化赛道过滤 |
| 本部门最多2票，其他部门合计最多2票 | `execute` 分别检查本部门与其他部门票数；两组额度独立，各可投0、1或2票，不能互相挪用，不校验跨部门占比 |
| 每条候选提名最多1票 | 选票按 `(idea_id,user_id)` 区分；`submit` 去重并跳过已投记录，重复提交不会加票或撤票 |
| 名册、部门来源 | `NomineeDirectory.resolveParticipant` 优先使用账号非空 `orgCode`，否则依次通过邮箱前缀、姓名唯一匹配BD名册；部门取组织代码中第一个“-”前的部分。候选身份优先取 `nomineeUserId`，旧数据缺少该字段时回退到创建人；新增投票时无法解析身份或部门则拒绝 |
| 并发约束 | 事务内获取案例锁和投票用户行锁，再读取选票并校验；同一用户跨候选人的增删串行处理 |
| 票篮与提交 | 点击候选人按钮只增删本地票篮，点击 `Submit` 才调用 `submit` 正式提交；已提交选票计入后续提交的额度。一次提交在事务内整体成功或回滚 |
| 撤票与重选 | 已提交候选人的按钮打开 `My voting records`，在记录中删除本人选票后可重新选择并提交；删除不校验部门比例或先后顺序，重复删除不会生成选票。后端另有按评选、赛道或全部清空本人选票接口 |
| 失败时保留状态 | 提交成功后才清空票篮并更新已提交状态，失败保留票篮并提示错误；删除记录成功后才更新前端票数 |

当前规则已不再要求“跨部门至少50%”，也不要求投满4票。例如本部门2票、其他部门0票允许；本部门1票、其他部门3票不允许。没有独立的“禁止投自己”规则；自己属于本部门，占用本部门最多2票的额度。

## 当前操作流程与中文提示差异

1. 登录后选择候选人，加入票篮；再次点击未提交的候选人可从票篮移除。本地保存票篮不等于正式投票。
2. 点击 `Submit` 将票篮提交到后端；成功后打开 `My voting records`，可从账号菜单再次进入查看。
3. 修改已提交选票时，先在投票记录中删除，再选择候选人并重新提交。点击已提交候选人的按钮只会打开记录，不会直接撤票。

`ProjectShowcase.tsx` 仍有“点赞后自动保存”和“每位候选人最多1票，再次点击即可取消”的中文提示，与以上流程不一致；本次只记录差异，未修改页面文案。后端仍保留单候选人的切换投票接口 `execute`，但不能据此把当前票篮流程描述为点击即正式投票或撤票。

代码依据（相对于 `app/`）：

- `hackhub-api/src/main/java/wtf/hackhub/application/idea/VoteIdeaUseCase.java`：额度、提交、删除与清空。
- `hackhub-api/src/main/java/wtf/hackhub/application/idea/NomineeDirectory.java`：身份和部门识别。
- `hackhub-app/src/pages/ProjectShowcase.tsx`：`handleVote`、`submitCart`、`deleteVotingRecord` 及中文提示。

## 相对规则0908文档的缺项（本次未实现）

1. **审核门槛**：当前 `VoteIdeaUseCase.execute` 和调用它的 `submit` 未检查候选人审核状态，不能声称只有经理审核通过的候选人能投。本次未补充审核校验。
2. **投票阶段与截止时间**：当前 `execute`、`submit`、`deleteRecord`、`clearTrack`、`clearAll` 未校验 `associate-voting` 阶段、活动关闭状态或投票起止时间。页面展示日期不等于后端会到期禁止提交或撤票；本次未实现阶段门槛或截止锁定。
3. **入围快照**：没有每赛道前30名及第30名同票全部入围的不可变快照；前端仍保留旧的10人入围/5人决赛常量，不能作为新规则依据。
4. **票数可见性**：员工候选人卡片和接口仍有实时总票数，尚未只显示本人是否投票。
5. **委员会范围**：当前有指定评委和加权评分实现，但未基于入围快照限制仅对入围人评分，阶段结束锁分也未实现。
6. **票篮统计**：当前非模态票篮显示未提交候选人总数及各评选、赛道的待提交数量 `/4`；不代表包含已提交选票的剩余额度，也未分别汇总本部门与其他部门可用票数。实际额度由后端提交时校验，不再以跨部门比例作为规则。
7. **特殊票数调整**：新文档的超级管理员审计加票、反向撤销与评分代改审计未包含在当前点赞系统内。

此外，后端总票数上限 `app.voting.max-votes-per-track` 当前配置为4，两个部门组的上限在代码中分别固定为2；单独提高总上限不会提高部门额度。前端说明固定为4票，`digitalPioneer.ts` 仍保留 `minimumOutsideDepartment: 2` 旧常量，不能将其解释为当前后端要求至少投2张跨部门票。
